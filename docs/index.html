Quick start · your machine

Clone it and it runs.

git clone https://github.com/LampOfSocrates/cupel.git
cd cupel
npm install
npm start

Cupel
  UI       http://localhost:5173
  Backend  bundled demo mock · http://localhost:4010
           storage: local · mock/cupel-mock.sqlite (local file, this machine only)

One command starts the interface and a demo backend, and tells you which backend you are on and where your data lives. It is a real, stateful backend — chat with SSE streaming, evaluations, versions, judgments, task queue — kept entirely in one SQLite file on your machine. Nothing leaves it; delete the file and you are back to the seed.

Requirements: Node ≥ 22.18 and Python 3.11+ with the mock's dependencies. Fill the app with more data while it runs: npm run simulate.

Quick start · make it yours

One command → an app with your name on it.

The command asks one question per family — chat, conversations, agents, evaluations, traces, the eval workbench, and so on — and each answer changes the app it writes:

npm run create -- "My Product"
→ my-product-ui/ — npm install && npm start
mine

That family calls your backend.

mock

The bundled backend serves it, and every screen it answers says served by mock. No guessing which half is real.

hide

No nav entry, no route, no requests. That part of the product does not exist.

  1. You are evaluating it

    Clone and npm start. The bundled backend serves everything, seeded with realistic conversations — no questions, no keys, no signup.

  2. You have an agent on HTTP and no spec

    The common case, and the one most tools cannot serve. Hand over the URL and how it streams:

    npm run create -- "My Product" \
  --agent-endpoint http://localhost:8000/chat --stream sse

    Your agent answers in a real chat UI. Everything else is mocked and badged until you want it.

  3. You have a backend with an OpenAPI document

    Its per-family conformance becomes the suggested answers — full means mine, anything less means mock, because a half-reachable family is a screen that half-works.

    npm run create -- "My Product" --openapi https://api.example.com/openapi.json

  4. Your backend already speaks the contract

    Point and go — and check it any time with npm run ready -- <your-openapi>, which reports full / partial / none per family. What it checks, what it deliberately does not, and how it reads a backend that spells out every agent as its own route: the readiness guide.

Every answer is written into one file you can edit afterwards, and the generated folder is a copy you own — editable, unencumbered, and honest about the fact that it receives no upstream fixes. Your product name, not "Cupel", is what your users see.

A typical day with Cupel

Prove the change was an improvement.

  1. Talk to the agent

    Real conversations accumulate — from you, your users, or a headless client posting through the same public API.

  2. Change the instructions

    Every save writes a new version. Nothing is ever overwritten, so v14 is still there when v15 disappoints.

  3. Replay yesterday's conversations against it

    Each turn re-runs under the context it originally recorded — same date, same timezone — so the only thing that varies is your change.

  4. Read the verdict

    Baseline beside each candidate, filling in live. Score with a judge and read its reasoning. Every past score is kept.

Why “cupel”

A cupel is the shallow bone-ash dish used to assay silver. Molten metal is held in it under heat: the lead and impurities are absorbed into the dish, and what is actually valuable stays behind. It seemed like the right name for a tool whose job is telling you whether the change you just made was worth keeping.
